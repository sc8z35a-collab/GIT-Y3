# KIWAMI MOBILE CORE 1.0 — POCO F7 を大前提とした端末適応エンジン

基準端末は **POCO F7**：Snapdragon 8s Gen 4（4nm、Cortex-X4 3.21GHz ×1 ＋ Cortex-A720 ×7）、Adreno 825、6.83インチ 1280×2772 AMOLED 120Hz（約447ppi）、12GB LPDDR5X、UFS 4.1。

この端末で **「常に 120Hz でカクつかず、熱くなりにくく、音とバイブが画面とぴったり合う」** ことを目標に設計しました。実装は `src/engine/mobile/KiwamiMobileCore.ts` と `src/engine/mobile/HapticSync.ts` です。検証は `npm run test:mobilecore`（26項目）で行います。

## 1. 端末の判定 (`classifyDevice`)

起動直後に `probeDeviceSignals` が次の情報を集め、端末に合わせた初期設定を選びます。

| 信号 | 取得方法 | POCO F7 での値 |
|---|---|---|
| GPU名 | `WEBGL_debug_renderer_info` | `ANGLE (Qualcomm, Adreno (TM) 825, OpenGL ES 3.2)` |
| リフレッシュレート | rAF の間隔を20回測った中央値を、実在する周波数に丸める | 120Hz |
| コア数 / メモリ | `hardwareConcurrency` / `deviceMemory`（Chrome では最大 8 と表示） | 8 / 8 |
| タッチ端末かどうか | `(pointer: coarse)` | true |

**Adreno 825 ＋ 8コア ＋ 120Hz** がそろうと「POCO F7 級」と判定し、次の設定で始めます。

- 120fps 目標、FHD、動的解像度の下限 0.62、Shadow Flame Flash、JSound Pro 品質
- 12GB RAM を活かし、**HD手肌テクスチャ（約106MB）を待機中に事前生成**（ズームしたとき待たずに高精細になる）
- 音の物理合成ワーカーは **3本**（Cortex-A720 側で動かし、Cortex-X4 はメイン描画に残す）

GPU名が隠されているブラウザでも、8コア・8GB以上・90Hz以上なら高性能端末とみなします。見込みが外れた場合は、次のフレームペーサーが約1秒で設定を下げます。

## 2. 閉ループ・フレームペーサー (`KiwamiFramePacer`)

120Hz の有機EL画面では、フレームの表示間隔は必ず垂直同期（約8.33ms）の整数倍になります。そのため「処理時間」ではなく **「同期を逃した割合」** を0.5秒ごとに測って制御します。

1. **使うのは割り切れるレートだけ**：120Hz パネルでは 120 → 60 → 40fps の3段だけを使います。90fps だと 1同期と2同期のフレームが交互になり、目に見えるカクつき（ジャダー）が出るためです。
2. **動的解像度**：1.0 → 0.9 → 0.8 → 0.72 → 0.64 → 0.56 の段で解像度を切り替えます。描画バッファを作り直すのは段が変わったときだけです。
3. **上げるときは「試行」**：解像度やレートを上げたあと最初に取りこぼしが出たら、すぐ元に戻します。次に試すまでの待ち時間は 4→8→16→32秒と倍々に延ばすので、上下を繰り返すことはありません。
4. **発熱の検知**：20秒以上安定していた設定で急に取りこぼしが出たら、端末の発熱による性能低下（サーマルスロットリング）とみなし、**45秒間 60Hz に抑えて冷却**します。冷却が終わったら、まず解像度の調整で 120Hz に戻ることを試します。
5. **待機中の省電力**：試合中でなく、カメラも動かず、3秒間タッチがなければ 60Hz に落とします。次のタッチで即座に 120Hz に戻ります。

取りこぼしの判定は「本来の間隔 ＋ 同期の半分」より長いフレームです。（1.5倍という判定だと、60fps 段の25ms フレームがちょうど境目に乗ってしまうため、この形にしました。）

### シミュレーション検証（120Hz パネルを模擬）

| 状況 | 結果 |
|---|---|
| 軽い（4.5ms/フレーム） | 120Hz・解像度1.0のまま、変更0回 |
| 重い（全解像度で11ms） | 1.0秒で下げ始め、解像度0.8・120Hz に収束。60秒で失敗した試行は3回だけ。収束後の取りこぼし 0.87% |
| 極端に重い | 解像度の下限（0.64）まで下げたあと、ジャダーの出ない 60Hz 段へ |
| 発熱（25秒後に負荷2倍） | 冷却は1回だけ（30〜68秒はずっと60Hz）。そのあと解像度0.72で 120Hz に復帰、取りこぼし 0% |
| 放置 | 3秒で 60Hz、タッチした瞬間に 120Hz |

## 3. 音と映像のずれをなくす予約再生 (`computeRevealSchedule`)

「ポン！」で手が見えるフレームの時刻を、`AudioContext.getOutputTimestamp()` を使ってオーディオ側の時計に変換します。そこから音の出力遅延（Bluetooth イヤホンでは約200ms）を引き、画面表示までの遅延（1.5フレーム）を足します。

$$t_{\text{音の開始}} = t_{\text{表示}} + L_{\text{映像}} - L_{\text{音}}$$

こうすると、手が**見えた瞬間に音が耳に届きます**。Bluetooth イヤホンなら、表示の187.5ms前に再生を始めます。

## 4. 音から作るバイブ (`extractHapticPattern`)

Vibration API はモーターのオン/オフしかできません。そこで24msごとの時間枠の中でオンの長さを変える（PWM）ことで、強さを表現します。

- 実際に鳴っている激突音の波形（耳に届くのと同じデータ）から6ms ごとの音量を取り、強さ^0.8 を枠内のオン時間にします。音の立ち上がり（アタック）は強めに出します。
- **どの時間枠でも時計を1枠ぶん進める**ので、音の隙間や弱い部分があっても、k番目のパルスは必ず k×24ms に始まります。音より前に無音がある場合は `[0, 24, …]` のように最初に休みを入れます。
- 発火時刻は「表示時刻 ＋ 画面遅延 − モーターの立ち上がり18ms」です。モーターの振動が最大になる瞬間を、手が見える瞬間に合わせています。

## 5. HUDを避けたカメラ中心 (`computeHudFraming`)

縦長の画面（20:9）では、下の「手」ボタン列が画面の下4分の1を覆うため、手が半分ボタンに隠れていました。そこでカメラを動かすのではなく、**投影の中心だけをずらしています**（`camera.setViewOffset` による斜め投影）。カメラの注視点が、上のバーと下のボタン列にはさまれた見える範囲のちょうど中央に来ます。

- POCO F7 の縦画面（上のバー 56px、ボタン列 173px）では、注視点が **58.5px 上**へ移ります。
- ずらすのは投影だけなので、遠近感、被写界深度、影、5K写真（ずらす前のカメラから自分で範囲を切り出す）には影響しません。
- ボタン列の高さが変わっても、時定数120ms でなめらかに追従するので映像が飛びません。PV（紹介映像）中はずれを0に戻します。

## 6. そのほかの POCO F7 向け最適化

- **シェーダーの事前コンパイル**（`compileAsync`）：最初の数フレームで引っかからないようにします。
- **タッチの即応**：手のボタンは `pointerdown`（指が触れた瞬間）で選ばれ、8ms の短いバイブが返ります。`click` を待つ約100ms の遅れがありません。
- **再生先の自動判定**：スマホでは本体スピーカー用の音作り（仮想低音、スピーカー保護、3バンド音圧調整）を初期値にします。イヤホンを使うときはスタジオで切り替えられます。
